# 提升 IAG（RAG）准确率的关键步骤：从 60% 到 85%

> 本文源自彭宇的技术分享，讲解如何将 IAG 系统的准确率从 60% 提升至 85%，涵盖数据处理、查询改写、混合检索、效果评估四个关键环节。附篇补充了工业落地中容易被忽视的高价值优化点及五种 RAG 架构的完整拆解。

---

## 一、背景与问题

在 IAG（Intelligent Augmented Generation，智能增强生成，俗称 RAG）项目的 Demo 阶段，系统往往表现流畅，但一旦上线面对真实用户，准确率往往骤降至 **60% 左右**，剩余 40% 的问题无法被正确回答，形成一个难以填补的"效果黑洞"。

本文拆解一个真实的工业级优化案例，展示通过以下四步关键改进，如何将准确率硬生生提升 25 个百分点。

---

## 二、数据处理：NLP 动态切分

### 典型错误做法

切分文档时直接用脚本按固定 token 数（如 500）一刀切断。这是 **实验室做法**，存在两个严重问题：

- 将一句完整的关键信息拦腰截断，后续检索时大模型读到的就是**残缺的碎片**，无法正确回答问题。
- 将表格内容切碎，导致结构化信息丢失。

### 工业级做法：NLP 动态切分

不依赖死板的计数器，而是引入 NLP 模型完成以下工作：

1. **语义边界识别**：识别句子、段落、自然章节的边界。
2. **结构感知**：识别 Markdown 标题、HTML 标签等文档结构标记，在结构完整处切分。
3. **重叠窗口（Sliding Window）**：在切分时额外保留 100–200 个 token 的重叠区域，保证上下文连贯，类似于接力赛中交接棒的"胶棒"机制。

> **优化效果**：仅此一步，不更换任何模型，准确率可直接提升 **15%**，是性价比最高的优化手段。

---

## 三、在线查询：Query 改写与语义校验

### 问题：用户 Query 普遍过短

用户在实际场景中经常只输入两三个字，例如"怎么退款"。这类 Query 语义模糊，直接检索效果很差。

### 常用方案：Query 扩写

通常会用一个小模型对 Query 进行扩写，生成多个语义变体，再分别进行检索，以提升召回率。

### 大坑：扩写模型幻觉

扩写模型一旦产生幻觉，后果极为严重——例如将"怎么退款"改写成"怎么赚钱"，方向完全相反，检索结果将彻底失效，引入大量噪声。

### 解决方案：语义校验（Semantic Guard）

**在改写后、检索前，必须加一道语义校验**：用向量模型计算**改写后 Query 与原始 Query 的相似度**，如果余弦相似度低于 **0.8**，说明改写发生了偏移，直接丢弃该改写结果。

```
原始 Query → 小模型扩写 → 语义校验（相似度 ≥ 0.8？） → 丢弃或进入检索
```

> 语义校验是大多数教程不会提及但至关重要的环节，是防止系统"自我引入噪声"的关键护栏。

---

## 四、混合检索：分数归一化与策略路由

### 核心挑战：分数量纲不统一

RAG 的心脏环节是**混合检索**（向量检索 + 关键词检索），但存在一个经典陷阱：

- **向量检索得分**：归一化到 `[0, 1]` 区间
- **BM25 关键词检索得分**：可能是 10、20，甚至更高

两者量纲完全不同。如果简单相加 `score = a × vec + b × bm25`，BM25 分数一高，向量分就会被完全淹没，混合检索直接失效。

### 错误做法

```python
# 拍脑袋定权重 —— BM25 分数高时会吞掉向量分
score = 0.5 * vector_score + 0.5 * bm25_score
```

### 工业级做法 1：LambdaMART 统一打分

不靠人工拍权重，而是使用轻量级排序模型（如 LambdaMART）将所有检索特征（向量相似度、BM25、文本长度、文档质量等）**统一映射到同一维度**进行打分。专业的事情交给专业的模型。

### 工业级做法 2：策略路由（Strategy Routing）

重排序（Re-ranker）模型效果好，但计算成本高（单次约 200ms），高并发时系统会直接崩溃。

解决方案：**按问题复杂度动态路由**

- **简单问题** → 直接走向量检索（Dense），毫秒级响应
- **复杂问题** → 开启重排序，用好钢在刀刃上

```
Query 复杂度判断
    ├── 简单（短 Query、事实性问题）→ 向量检索
    └── 复杂（长 Query、多跳推理） → 混合检索 + 重排序
```

> 策略路由兼顾了效果与性能，是面试中常被追问的高频考点。

## 五、效果评估：分层指标体系

### 常见误区

只汇报"用户满意度 85%"过于笼统，无法指导下一步优化方向。用户点"不满意"的原因可能是：

- **检索问题**：答案根本没被召回
- **生成问题**：资料里是 A，大模型却生成了 B（幻觉）

### 指标拆解

| 指标 | 英文名 | 衡量内容 | 问题定位 |
|------|--------|----------|----------|
| 上下文召回率 | Context Recall | 答案是否在检索回来的切片中 | 检索问题 |
| 忠实度 | Faithfulness | 生成内容是否忠实于检索到的资料（有无幻觉） | 生成问题 |
| 首轮解决率 | First Turn Resolution | 用户问题是否在第一轮就得到解决 | 整体体验 |

将指标监控起来，才能真正知道下一步该优化检索还是优化生成。

## 六、总结：四步走通工业级 IAG

| 步骤 | 要点 | 关键行动 |
|------|------|----------|
| **1. 切分** | 别暴力截断 | 用 NLP 动态切分 + 重叠窗口 |
| **2. 排序** | 别瞎加权重 | 用 LambdaMART 统一打分 |
| **3. 防噪** | 改写完必须校验 | 语义相似度回检，阈值 0.8 |
| **4. 指标** | 别只看满意度 | 拆解 Context Recall、Faithfulness 等细分指标 |

> 这四步走通，IAG 才能从 Demo 玩具蜕变为真正的工业级产品。建议对照以上框架检查自身项目，逐项排查这些坑是否都已踩过。

## 附、容易被忽视的高价值优化点

以下内容原视频未涉及，但在实际工业落地中往往能带来显著效果提升，属于「做完四步之后还能继续挖」的方向。

---

### 附-1 Chunk 元数据富化（Metadata Enrichment）

大多数实现只把文本切成块存入向量库，但丢失了大量可检索的**结构化信息**。

**典型可附加的元数据字段：**

| 字段 | 示例值 | 作用 |
|------|--------|------|
| `source` | `产品手册 v2.3.pdf` | 按文档来源过滤 |
| `page` | `12` | 返回原文档位置，便于人工核实 |
| `heading_path` | `第3章 > 3.2 退款政策` | 判断文档层级，决定是否需要跨块召回 |
| `content_type` | `表格 / 代码 / 正文` | 不同类型用不同 Prompt 模板 |
| `last_updated` | `2025-08-01` | 优先召回最新政策文档 |

> **效果**：加一层元数据过滤或 boost，可将某些垂类场景的准确率再提升 5–10%。

---

### 附-2 多数据源处理：PDF 解析与异构数据源专项

多数据源下的 RAG 问题非常庞杂，尤其是 PDF 是公认的"地狱级数据源"。本节从解析层、异构层、内容层三个维度系统梳理高频问题及应对方案。

---

#### 2-1 PDF 解析层：六类核心问题

##### 文本型 PDF vs 扫描件 PDF

| 类型 | 定义 | 解析难度 | 典型问题 |
|------|------|---------|---------|
| **文本型 PDF** | 底层是文字，可直接复制 | 低 | 布局和样式信息丢失 |
| **扫描件 PDF** | 本质是一张图片，需要 OCR | 高 | OCR 错误率高、表格无法结构化 |

**扫描件的具体问题**：
- OCR 识别率通常在 85%–95%，合同编号、日期、金额等关键字段一旦识别错误，整个答案就错
- 表格 OCR 后变成一堆无序文字，列对齐关系完全丢失
- 手写签名、盖章、划线批注区域常被识别为乱码
- 印章颜色深浅、纸张褶皱会导致识别率参差不齐

```
原始扫描件:
┌─────────────────────────────┐
│  第三条  退换货期限           │
│  购买商品之日起 15 日内...    │
│  ⚠️ "15日"OCR成"I5日"       │
│  ⚠️ 条文编号和内容被截断      │
└─────────────────────────────┘

解析结果 → "购买商品之日起 I5 日内..." → 模型读到"I5"直接困惑
```

##### 复杂布局问题

文本型 PDF 同样面临非自然阅读顺序的布局挑战：

| 场景 | 具体表现 | 对 RAG 的影响 |
|------|---------|--------------|
| **双栏排版** | 论文、报告类 PDF 大量使用双栏 | 按从上到下硬读会把第一栏末尾和第二栏开头混在一起，形成语义混乱的碎片 |
| **图文混排** | 产品手册中图片和说明交叉排列 | 图片说明文字被图片打断，语义块被截断 |
| **侧边目录** | 左侧固定显示章节目录 | 目录文字混入正文内容 |
| **页眉页脚** | 每页重复显示公司名、文档标题、页码 | 重复信息占用 Chunk token，挤占有效内容 |
| **跨页表格** | 一个表格横跨多页 | 表格被切成碎片，列对应关系完全丢失 |

**双栏解析的经典坑**：

```
原文双栏布局:
┌──────────────┬──────────────┐
│  第一栏第一段  │  第二栏第一段  │
│  第一栏第二段  │  第二栏第二段  │
│  第一栏第三段  │  第二栏第三段  │
└──────────────┴──────────────┘

错误解析（从上到下硬读）:
"第一栏第一段 → 第二栏第一段 → 第一栏第二段 → 第二栏第二段..."
          ↑
    语义在此被打断
    "第一栏第二段"的开头接上了"第二栏第一段"的结尾
    形成语法混乱、语义错位的垃圾文本
```

##### 表格解析是公认难题

表格在 PDF 中是最难正确解析的元素，没有之一。

**边框丢失**：

```
原始表格（有边框，语义清晰）:
┌─────┬─────┬─────┐
│ 城市 │ 温度 │ 天气 │
├─────┼─────┼─────┤
│ 北京 │ 25℃ │ 晴  │
└─────┴─────┴─────┘

解析后（边框丢失，语义模糊）:
"城市 温度 天气 北京 25℃ 晴"
→ 模型无法知道 25℃ 属于北京还是下一行
→ 任何基于表格的数字问答都会出错
```

**合并单元格**：年度财务报表大量使用多级表头和合并单元格，解析后行与行之间的对应关系几乎不可能还原。

**布局用表格 vs 数据表**：PDF 不区分两种用途，有时表格只是用来做排版对齐（如把几个并排图片框起来），OCR 会把它当成真正的数据表来处理。

#### 2-2 多数据源异构问题

##### 格式全家桶

一个典型的企业知识库往往同时包含：

```
PDF（合同、报告、手册）       ← 最难处理
├── Word（政策文档、通知）    ← 样式丰富，标题层级复杂
├── Excel（数据表格、报表）   ← 需要按行列结构解析，不是纯文本
├── HTML（官网、Wiki）       ← 结构相对清晰，但有广告/导航干扰
├── Markdown（技术文档）     ← 最友好，结构最干净
├── PPT（演示材料）          ← 大量文字在图片里
├── 邮件/聊天记录（客服数据） ← 碎片化、口语化
└── 数据库（结构化数据）      ← 需要 Text-to-SQL 而不是 RAG
```

每种格式的最优解析策略各不相同，强行统一处理必然导致某些数据源质量崩塌。

##### 元数据结构不一致

不同来源文档的元数据质量差异巨大：

| 来源 | 可能有元数据 | 可能缺失 |
|------|-------------|---------|
| 企业内部系统 | 部门/作者/创建时间/密级 | 版本号、关联产品线 |
| 第三方报告 | 发布机构/发布日期/页数 | 适用范围、假设条件 |
| 用户上传文档 | 文件名/上传时间 | 任何结构化元数据 |

**后果**：当用户问「这份报告的结论是什么」，同一主题有多份版本（v1.0/v2.0/终稿）时，系统可能把草稿版本的结论也一并召回，造成混淆。

##### 信息冲突问题（最棘手）

多数据源最棘手的问题：**同一个知识点在不同文档里说法不一致**。

```
文档A（2023年产品手册）:
"本产品保修期为购买之日起24个月"

文档B（2024年官网更新）:
"自2024年1月1日起，保修期调整为36个月"

文档C（客服话术库）:
"我们产品保修一年，终身维护"

用户问："这个产品保修几年？"
→ 三个来源三种说法，系统全召回，模型可能采信了最老的文档A
→ 如果选错了，用户拿着"一年"的答案去维权，踩大坑
```

#### 2-3 内容质量层问题

##### 重复内容

一份完整的政策文件可能被拆成多份文档存放：

```
集团总纲.pdf
    └── 第八章 退货政策

各地区附录/
    ├── 华北区退货细则.pdf（重复了第八章的部分内容）
    ├── 华东区退货细则.pdf（同上，但有个别地区特殊条款）
    └── 华南区退货细则.pdf（同上）

用户问"退货要什么条件"
→ 可能同时召回总纲 + 3个地区附录
→ 总纲讲通用规则，附录只讲地区差异
→ 模型看到4份文档，容易把地区差异当成通用规则
```

##### 知识陈旧

| 类型 | 保鲜期 | 问题 |
|------|-------|------|
| 法律法规 | 长但有窗口期 | 新法实施后旧法未及时下架 |
| 产品参数 | 短，迭代频繁 | 新款已上线，旧款参数还在知识库里 |
| 业务流程 | 中，受组织调整影响 | 部门合并/拆分后老流程图还在 |
| 客服话术 | 短 | 新政策推出后旧话术仍在被召回 |

---

#### 2-4 Embedding 和 Chunk 策略的连锁问题

##### 不同内容类型需要不同切分策略

```
代码片段（需要完整保留函数体）:
→ 按固定token数切分会切断函数体，Embedding后语义完全破碎

表格（需要保持行列关系）:
→ 按段落切分会切断列信息

长文本（需要章节语义完整性）:
→ 按固定token切分会导致同一章节的内容分散到不同 Chunk
```

##### 通用 Embedding 模型的短板

通用 Embedding 模型对以下内容效果较差：

| 内容类型 | 问题 |
|---------|------|
| **专业术语密集的法律/医疗文本** | 同一术语在不同领域含义不同 |
| **代码及其注释** | Embedding 无法理解代码逻辑 |
| **数学公式** | LaTeX 符号在 Embedding 层面没有语义等价 |
| **表格数据** | Embedding 把表格当成普通段落处理，行列关系丢失 |

#### 2-5 高频问题清单与应对优先级

| 问题 | 频率 | 严重程度 | 解决难度 |
|------|------|---------|---------|
| 扫描件 OCR 识别错误 | ⭐⭐⭐⭐⭐ | 高 | 中（需换OCR引擎+人工校验） |
| 跨页表格被切断 | ⭐⭐⭐⭐⭐ | 高 | 高（需专用表格识别模型） |
| 双栏排版解析乱序 | ⭐⭐⭐⭐ | 高 | 高（需布局分析算法） |
| 不同来源信息冲突 | ⭐⭐⭐⭐⭐ | 高 | 高（需冲突检测+优先级机制） |
| 表格被当成普通文本 | ⭐⭐⭐⭐ | 高 | 高（需专用表格解析） |
| 多版本文档并存 | ⭐⭐⭐⭐ | 高 | 中（需元数据+时效性过滤） |
| 页眉页脚混入正文 | ⭐⭐⭐ | 中 | 低（固定规则过滤即可） |
| 嵌入图片的文字 | ⭐⭐⭐ | 高 | 高（需多模态OCR） |
| 代码块被切碎 | ⭐⭐⭐ | 中 | 中（需按代码结构切分） |

#### 2-6 分层解决思路

```
第一层（快速止血，1–2天）
├── 规则过滤页眉页脚、页码等固定干扰项
├── 按文档类型选择解析器（PDF.js / PyMuPDF / Marker）
├── 元数据强制补全（文件名、上传时间作为兜底元数据）
└── 时效性过滤（根据 last_updated 降权或丢弃过期文档）

第二层（系统优化，1–2周）
├── 引入专用表格解析（Table Transformer / StructData）
├── 针对扫描件使用高精度OCR（PaddleOCR + 人工抽检）
├── 按内容类型分别切分（代码用AST、表格用行列、文本用NLP）
└── 文档版本去重（按标题+时间聚类，保留最新版本）

第三层（深度治理，持续迭代）
├── 构建知识冲突检测机制（同实体多文档出现时触发人工审核）
├── 针对垂直领域微调 Embedding 模型
├── 建立数据源质量评分体系（定期评估各来源的准确率贡献）
└── 多模态解析（图片内文字、图表说明等全部纳入索引）
```

### 附-3 检索后处理（Post-Retrieval Processing）

检索回来 Top-K 个 Chunk 后，直接拼进 Prompt 效果往往不是最优的，以下是几个经过验证的后处理手段：

#### 1. 去重与 MMR（最大边际相关性）

如果多个 Chunk 内容高度重叠，简单拼接会浪费 context window 长度。使用 **MMR** 在召回率和多样性之间做平衡：

```python
# 伪代码示意
selected = []
for doc in candidates:
    score = relevance(doc, query) - λ * max_similarity(doc, selected)
    selected.append(doc)
```

#### 2. Context Window 管理

超过 LLM 的 context limit 时，优先保留与 Query 相似度最高的块，同时确保**首块和末块的完整度**（LLM 对首尾位置的内容记忆力更强）。

#### 3. 引用溯源（Grounded Citation）

要求模型生成时附带 Chunk 编号或来源，输出格式如：

```
答案：根据《退款政策》第3.2条，用户可在下单后7天内申请退款。
来源：[chunk_003] [chunk_007]
```

引用信息既提升了用户信任度，也极大方便了人工 Bad Case 溯源。

---

### 附-4 生成层：Prompt 工程与幻觉抑制

#### 拒答机制（Default-to-No）

在 Prompt 中明确设定"当检索结果不足以回答问题时，直接回复'抱歉，我无法根据现有资料回答该问题'"，而非强行生成。这是减少幻觉最简单有效的手段。

#### Few-Shot 示例注入

在 Prompt 中加入 2–3 个「问题→参考切片→正确答案」的示例，可显著提升模型在特定垂直领域的表现。

#### 控制生成长度

根据 Query 类型（事实型 vs 解释型）动态调整 `max_tokens`，避免模型因"说不满"而产生幻觉填充。

---

### 附-5 可观测性：Bad Case 闭环

工业级 IAG 必须建立 **检索 → 生成 → 反馈** 的闭环：

```
用户 Query
    │
    ├─→ 检索层：记录 Top-K 得分、召回文档ID
    │
    ├─→ 生成层：记录回答内容、是否拒答
    │
    └─→ 反馈层：用户点踩 / 追问 → 触发 Bad Case 入库
              → 自动聚类相似 Query
              → 定期人工 review → 更新知识库 / 调整策略
```

建议接入一个轻量级的 Case Management 工具（如飞书多维表格、Notion），将 Bad Case 分成「检索问题」和「生成问题」两类，持续迭代。

---

#### 快速鉴别流程

```
用户点踩 / 回答错误
    │
    ▼
查看检索日志 Top-K Chunk
    │
    ├── 正确答案完全不在 Top-K 中 ──→ 检索问题 ──→ 排查切分 / Embedding / Query改写
    │
    └── 正确答案在 Top-K 中 ──→ 生成问题 ──→ 排查 Prompt / 幻觉 / 读取完整性
```

---

#### 检索问题（Retrieved Wrong Chunks）

**定义**：答案本来存在于知识库中，但检索阶段就没有把它捞回来，后续生成阶段自然无米下锅。

**典型特征**：回答内容空洞、答非所问；模型大量使用"根据我的理解"等模糊措辞；检索日志中 Top-K Chunk 与 Query 主题偏差较大。

| 用户 Query | 正确答案位置 | 检索实际召回 | 根因分析 |
|-----------|------------|------------|---------|
| "退货的运费谁承担" | 《售后政策》第5条：7天内运费由商家承担 | 召回的是《物流说明》中的运费计算公式 | 切分时把"售后政策"和"运费说明"切到了不同 Chunk，且 Query 中的"退货"和"运费"分别命中了不同语义簇 |
| "公司年假多少天" | HR 手册 v3.pdf 全公司年假制度 | 召回了"病假制度""调休规定"等多个相关但不正确的 Chunk | Query 太短（年假多少天），语义模糊，没有触发"年假"这一精确关键词 |
| "这个产品支持蓝牙 5.3 吗" | 产品参数表 P2，蓝牙版本 | 召回了产品介绍（讲功能体验）但没召回参数表 | 产品介绍和参数表被切成了不同文档，向量检索只匹配到了表面语义相似的介绍页 |

**修复方向**：检查切分策略是否破坏语义边界、Embedding 模型是否适配垂直领域、Query 改写是否引入了语义漂移、是否需要加元数据过滤。

---

#### 生成问题（Generated Wrong Answer）

**定义**：检索阶段已经把正确答案的 Chunk 召回来了，但 LLM 生成时出错——可能是幻觉、误解、格式偏差、信息遗漏等。

**典型特征**：检索日志显示 Top-K Chunk 中确实包含正确答案；模型仍然生成了错误内容或遗漏了关键信息；回答中有模型"自行发挥"的成分。

| 用户 Query | 召回 Chunk（包含正确答案） | 模型生成 | 根因分析 |
|-----------|------------------------|--------|---------|
| "退款多久到账" | 支付宝/微信 1-3 个工作日，银行卡 3-5 个工作日 | "退款将在 7 个工作日内到账" | 没有读取 Chunk 中的分支条件，直接生成了模糊"标准答案"，属于读取不完整 |
| "订单A123能退吗" | 订单A123属于定制商品，定制商品不支持退换 | "您好，您的订单支持退换，请在APP内申请" | 模型根据训练数据中的通用客服话术生成了肯定回复，与 Chunk 中的限制条件冲突，属于训练数据与检索知识冲突的幻觉 |
| "第三段讲了什么" | 一段关于产品定价策略的描述 | "第三段主要介绍了产品的功能特点" | Chunk 被成功召回，但模型用自己的理解替换了段落主题，属于理解偏差 |
| "请列举所有支持的支付方式" | Chunk 中列出了 5 种支付方式 | 只列举了 3 种，遗漏了"花呗分期"和"企业转账" | 模型擅自压缩了答案，属于信息遗漏幻觉 |

**修复方向**：优化 Prompt 中的指令约束（强制要求参考 Chunk）、补充 Few-Shot 示例、调整 max_tokens 防止截断、增强拒答机制。

---

#### 串联案例：一个 Query 两种问题的不同表现

> 用户问："我去年买的这款吹风机还在保修期内吗？"

| 问题类型 | 检索侧表现 | 生成侧表现 |
|---------|-----------|-----------|
| **检索问题** | 知识库里有购买凭证和保修条款，但购买日期存在 PDF 附件中，PDF 未被解析，导致"购买时间"未向量化 | 模型正确理解了保修条款，但因检索不到购买时间，只能给出一个通用模糊回答 |
| **生成问题** | 检索成功召回了购买记录（2024年1月购买）和保修条款（整机保修2年）两份文档 | 模型在计算日期时出错，说"您的产品已过保修期"，实际按日期计算仍在保修内，属于推理错误 |

---

## 附-6 RAG 架构选型：五种模式完整拆解

不同场景适用的架构完全不同，本节从原理出发，逐一拆解五种 RAG 架构的适用场景、实现细节和优缺点，并给出选型决策树和实战组合建议。

---

### 6.1 标准 RAG（Standard RAG）

#### 工作原理

最经典的两阶段架构：**检索 → 生成**。

```
用户 Query
    │
    ▼
┌─────────────┐
│  Embedding  │  ← 把 Query 向量化
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  Vector DB  │  ← 近似最近邻（ANN）检索 Top-K Chunk
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  LLM + P   │  ← Chunk + Query 拼成 Prompt，LLM 生成回答
└─────────────┘
```

#### 适用场景

- 单文档或文档集问答（如产品手册、内部知识库）
- Query 和答案**都在同一份文档内**，无需跨文档推理
- 数据量中等（万级 Chunk 以内）

#### 优点

- 架构简单，OpenAI 2020 年提出，生态成熟，文档丰富
- 端到端可控，可精确知道哪篇 Chunk 回答了问题
- 推理延迟低，工程实现成本低

#### 缺点

- **缺乏跨文档推理能力**：如果"退款政策的有效期是多久"这个答案跨越了「退款政策」和「时间计算规则」两个文档，标准 RAG 容易只召回一个
- **对多跳问题不友好**：复杂问题往往需要先聚合多个信息点再推理
- **幻觉风险**：LLM 可能用检索到的噪声片段"拼凑"一个看似合理但错误的答案

---

### 6.2 GraphRAG（知识图谱增强 RAG）

#### 工作原理

核心思想：**先从文档中抽取知识图谱，再用图结构做检索增强**。

微软在 2024 年提出了完整的 GraphRAG 方案，分两步走：

**Step 1 — 构建阶段（Indexing）**

```
文档集合
    │
    ▼
┌──────────────────────┐
│ LLM 实体关系抽取      │  ← 从每个 Chunk 中识别「实体」和「关系」
│ 例：退货政策 ──属于── 产品条款
└──────┬───────────────┘
       │
       ▼
┌──────────────────────┐
│ 构建知识图谱 (Graph)  │  ← 节点=实体，边=关系
└──────┬───────────────┘
       │
       ▼
┌──────────────────────┐
│ 社区检测 + 摘要生成    │  ← 将图划分为社区，每个社区生成全局摘要
└──────────────────────┘
```

**Step 2 — 检索阶段**

```
Query
    │
    ├──→ 传统向量检索（局部感知）  ← 回答具体事实性问题
    │
    └──→ 社区级别检索（全局感知）  ← 先定位相关社区，读摘要，理解全局背景
```

#### 适用场景

- **多文档、跨文档**的复杂知识库（如企业年报、法律文档、产品家族体系）
- 需要回答「某公司所有子业务线的 Q3 营收加起来是多少」这类**跨章节聚合问题**
- 答案需要**理解全局语义关系**，而非单点事实

#### 优点

- 解决跨文档多跳推理问题
- 对语义层面的「主题」类问题（而非事实查找）效果显著优于标准 RAG

#### 缺点

- 构建知识图谱需要**额外的 LLM 调用**（抽取实体关系），成本较高
- 图谱更新滞后于文档更新，需要增量维护机制
- 实现复杂度高，需要图数据库（如 Neo4j）支持

---

### 6.3 Self-RAG（自反思 RAG）

#### 工作原理

Self-RAG 由卡内基梅隆大学提出，核心创新是：**让 LLM 自己判断是否需要检索，以及检索到的内容是否有用**。

关键引入了五类特殊的反思 Token：

| Token | 含义 | 触发条件 |
|-------|------|----------|
| `[Retrieval]` | 需要检索 | 模型认为自身知识不足以回答 |
| `[Relevant]` | 检索结果相关 | Chunk 对 Query 有帮助，保留 |
| `[Irrelevant]` | 检索结果无关 | Chunk 与 Query 无关，丢弃 |
| `[Supported]` | 生成有据可查 | 生成内容得到 Chunk 支持 |
| `[Hallucinated]` | 生成存在幻觉 | 生成内容与 Chunk 不符 |

```
Query → LLM 判断是否需要检索
    │
    ├── [否]──→ 直接用 LLM 自身知识回答
    │
    └───[是]──→ 检索 Top-K Chunk
                     │
                     ▼
              逐个判断 Chunk 相关性
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
     [Relevant]             [Irrelevant]
          │                     │
          ▼                     ▼
     进入生成候选           丢弃，不参与生成
          │
          ▼
    生成回答，标注每句话的来源和可靠性
```

#### 适用场景

- **知识边界模糊**的场景，LLM 自身知识和外部知识混杂
- 需要**严格区分「我知道」和「我查到的」**的情况（如医疗、法律）
- 想让模型在生成过程中自我纠错，而不是后置校验

#### 优点

- 精确控制「用自身知识」和「用外部检索」的边界，减少不必要检索的延迟
- 生成时附带反思标记，可解释性强，便于 Bad Case 溯源

#### 缺点

- 需要训练或微调支持 Self-RAG 的专用模型（如 Self-RAG-7B），直接用通用 GPT 效果有限
- 推理时生成额外的反思 Token，有一定延迟开销

---

### 6.4 Corrective RAG（纠正式 RAG）

#### 工作原理

Corrective RAG 在标准 RAG 的基础上加了一层**检索结果质量校验**，在把 Chunk 送入 LLM 之前先过一遍"安检"。

```
Query
    │
    ▼
┌──────────────┐
│  向量检索     │  ← 召回 Top-K Chunk
└──────┬───────┘
       │
       ▼
┌──────────────────────────┐
│  答案召回验证（ARE）        │  ← 用验证模型判断 Chunk 是否真的能回答 Query
│  "Does this support        │
│   the answer?"            │
└──────┬───────────────────┘
       │
  ┌────┴────┐
  │         │
  ▼         ▼
[可信]    [不可信]
  │         │
  ▼         ▼
进入生成   丢弃 / 降权 / 用 LLM 补全
```

#### 关键模块拆解

**答案召回验证（Answer Recall Estimation）**：用一个轻量模型（如 DeBERTa）判断「给定 Query 和 Chunk，这个 Chunk 能否支撑出一个正确答案？」，输出 Yes/No 或概率分数。

**文档重排序（Document Re-ranking）**：经过校验的 Chunk 重新打分排序，优先使用高置信度的块。

**LLM 补全（Fallback）**：对被标记为"不可信"但仍有一定相关性的 Chunk，用 LLM 做「基于部分线索推理」，而非直接丢弃。

#### 适用场景

- **噪声较大的知识库**（如用户生成内容、爬虫数据、格式混乱的文档）
- 需要**在生成前过滤低质量检索结果**，防止幻觉扩散
- 适合「问答对」质量要求极高的场景（客服、医疗）

#### 优点

- 有效过滤噪声，从源头减少幻觉，比在生成层补救更高效
- 可与任何标准 RAG 架构叠加，是"增强插件"

#### 缺点

- 需要训练或微调一个专门的验证模型，初始成本较高
- 校验模型本身也可能误判，需要在准确率和召回率之间权衡

---

### 6.5 Grounded Citation（RAG + 引用溯源）

#### 工作原理

要求模型在生成回答时，**强制附带每句话对应的 Chunk 编号或来源文档**。这不是一个独立的架构，而是一种**生成侧的工程约束**，可叠加在任何一种 RAG 架构之上。

典型输出格式：

```
答案：根据《退款政策》第3.2条，用户可在下单后7天内申请退款。
来源：[chunk_003] [chunk_007]
```

实现方式有两种：

1. **Prompt 约束**：在 Prompt 中明确要求模型引用来源
2. **后处理抽取**：先生成回答，再用 NER 模型从回答中抽取可溯源的实体片段

#### 适用场景

- 需要**可审计、可追溯**的强合规场景（金融、医疗、法律）
- 面向 B 端客户，需要证明回答有据可查
- 作为 Bad Case 溯源的基础设施

#### 优点

- 几乎零额外成本（只需改 Prompt 或加一层 NER）
- 大幅提升用户信任度，是 B 端产品的"标配"能力

#### 缺点

- 依赖 Chunk 粒度的精确切分，如果 Chunk 本身信息残缺，引用也会失去意义
- 部分模型对引用格式的遵从度不稳定，需要针对调优

---

### 6.6 架构对比与选型决策树

#### 五种架构综合对比

| 维度 | 标准 RAG | GraphRAG | Self-RAG | Corrective RAG | + Grounded Citation |
|------|----------|----------|----------|---------------|---------------------|
| **核心能力** | 单跳事实问答 | 跨文档图推理 | 自主判断检索必要性 | 检索质量校验 | 生成可溯源 |
| **幻觉抑制** | ⭐⭐ | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| **多跳推理** | ⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ | ⭐ |
| **实现复杂度** | 低 | 高 | 高（需微调） | 中 | 低 |
| **额外 LLM 调用** | 无 | 多（抽取图谱） | 多（反思 Token） | 中（校验模型） | 无 |
| **适用数据规模** | 小~中 | 大规模复杂 | 中~大 | 任意 | 任意 |
| **知识更新频率** | 中（需重建索引） | 低（增量难） | 中 | 中 | 中 |

#### 选型决策树

```
你的 IAG 场景，最先问自己三个问题：

① 答案在单个 Chunk 里吗？
  ├── YES → 进入②
  └── NO（跨文档、需聚合） → GraphRAG

② 对幻觉的容忍度有多高？
  ├── 极高（允许自由发挥） → 标准 RAG
  ├── 高（希望有来源） → + Grounded Citation
  └── 低（不允许胡说） → 进入③

③ 数据质量如何？
  ├── 知识库干净规范 → Self-RAG
  └── 噪声多、格式乱 → Corrective RAG
```

#### 实战中的常见组合

| 组合 | 典型场景 |
|------|----------|
| **标准 RAG + Corrective RAG + Grounded Citation** | 快速上线，先解决"检索不准"和"无法溯源"两个基础问题 |
| **GraphRAG + Corrective RAG** | 大型企业知识库，文档质量参差，需要跨部门知识聚合 |
| **Self-RAG + Grounded Citation** | 医疗/法律问答，需要严格的事实性和可溯源性 |
| **GraphRAG + Self-RAG + Corrective RAG** | 超大规模知识库，对准确率和可审计性都有极高要求 |

---

### 6.7 落地顺序建议

如果从零开始搭建一个生产级 IAG，建议分三个阶段走：

```
阶段一（快速见效，1–2 周）
标准 RAG + Grounded Citation + 附-1 元数据富化 + 附-2 多数据源处理
→ 解决基础能用的问题

阶段二（稳定提质，1 个月）
Corrective RAG + Bad Case 闭环 + 附-4 Prompt 优化
→ 逐步消除幻觉，建立持续迭代机制

阶段三（能力升级，按需引入）
GraphRAG / Self-RAG（根据真实 Bad Case 数据决定）
→ 处理复杂场景，ROI 最高时再做
```

> **核心原则**：不要在第一阶段就强上 GraphRAG——构建知识图谱的工程成本和知识库维护成本会拖垮整个项目。先用标准 RAG 跑通全链路，拿到真实 Bad Case 数据之后，再决定是否需要引入更重的架构。
